# S3 JSON и Content Sync Worker

[Оглавление](README.md) · [Языки](08-seo-and-localization.md) · [Данные](10-backend-and-data.md)

## Задано

Готовые переводы находятся в S3 JSON; в архитектуре есть Content Sync Worker. Конкретный S3-провайдер, направление синхронизации, runtime Worker и место назначения не установлены. Название Worker само по себе не подтверждает Cloudflare Workers.

## Предлагаемая схема потока

Источник готовых переводов → S3-совместимое хранилище → Content Sync Worker → проверенная опубликованная версия → потребитель Next.js/API.

Один из кандидатов структуры: `releases/{version}/{locale}.json` плюс manifest с версией схемы, перечнем языков, контрольными суммами и временем публикации. Это пример, не существующий контракт.

## Предлагаемый алгоритм

1. Получить manifest и определить новую версию.
2. Загрузить набор файлов и проверить JSON-схему, размер, контрольные суммы, обязательные ключи и набор locale.
3. Подготовить версию целиком без переключения читателей.
4. Атомарно переключить указатель активной версии.
5. Инвалидировать зависимые кэши и записать итог без секретов.
6. При ошибке оставить последнюю исправную версию и сообщить о сбое.

Повторный запуск одной версии должен быть безопасен. Для параллельных запусков нужен механизм координации; выбор зависит от runtime. Нельзя считать ETag универсальной контрольной суммой содержимого без проверки провайдера и способа загрузки.

## Надёжность и доступ

Разделить право публикации и право чтения. Секреты хранения — только в соответствующих серверных окружениях. Публичными могут быть только предназначенные для публикации словари. Нужны ограниченные повторы, таймауты, метрики последней успешной версии, отставания и ошибок валидации.

Открыто: polling или события, источник истины, частота синхронизации, SLA, частичная публикация, destination (БД/кэш/объектное хранилище), rollback, формат rich text и обработка удалённых ключей.
