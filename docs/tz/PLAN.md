# План исполнения актуального ТЗ Beeloy

Этот план обновляет порядок работ, не отчёт о выполнении. Исторические результаты находятся в DONE.md и SPIKE-T05.md; текущий статус соответствия новой редакции — **не проверен**. Пользователь запросил исправление ТЗ, а не изменение кода или деплой.

## Источник и границы

Обязательны beeloy.org-витрина и beeloy.com-сообщество, OTP/Google/Facebook, Go/PostgreSQL без ORM/Redis, S3 JSON с готовыми переводами, Content Sync, Next.js/Mantine на Cloudflare, Hetzner/Compose, монорепо и остальные темы из 00-README §7. Подробности с [Т] не выдаются за исторические решения заказчика. Утверждённых сроков, команды и бюджета в доступном контексте нет.

## Порядок

Следовать T01–T57 из [09-tasks.md](09-tasks.md); идентификаторы задач не перенумерованы. Общие locale/glossary/en создаются в T01; базовые ACL-типы — T02; миграции 0001–0013 — T03. T38 расширяет frontend-контракты. T49 включает отдельную витрину apps/org. Финальная приёмка — T57 после всех T01–T56.

Для существующей реализации не пересоздавать каркас, не менять старые применённые миграции и не объявлять исторически выполненные задачи зелёными по новой редакции без проверки. Сначала сопоставить код контрактам; затем внести затронутые изменения и тесты; отдельно выполнить конечный прогон и записать новые результаты/непроверенное в DONE.

## Приоритет исправлений

1. Identity: вернуть Google/Facebook, атомарный OTP, безопасный onboarding/linking, публичный slug-check и защиту последнего active-admin.
2. Доступ: no-store для изменяемых данных/HTML/RSC, проверка цели комментариев и registry, доверенный ingress Worker→Caddy→Go.
3. Контент: неизменяемые S3-ключи, CAS manifest, запрет force-перезаписи, live только published_rev, повтор неудачного sync.
4. Мессенджер: ранняя идемпотентность, транзакционная проверка request cap, единый conversation-event, unread/mute и восстановление SSE.
5. Privacy/эксплуатация: фактическая очистка комментариев/связей, экспорт без staff-снимков, согласованный backup/restore PostgreSQL+S3, повтор удаления после restore.
6. Витрина .org, общая бренд-архитектура и полный набор тестов/документации.

## Действия оператора перед production

- DNS и hosting обоих доменов; api-site.beeloy.com, TLS Origin CA, AOP и firewall.
- SMTP, Google/Facebook applications и callback URLs, секреты API/Worker; provider scopes/flow проверяются по официальной документации при реализации.
- Приватный S3 и независимый backup bucket, раздельные credentials, проверка conditional writes и восстановления всех данных.
- Правила сообщества (документа на legal-сайте нет; остаётся `TODO-LEGAL`), сверка юристом документов на legal.beeloy.org (сроки/основания обработки), перевод миссии на 26 языков и проверка выборки машинных переводов, сверка списка 26 языков/default.
- Фактические end-to-end проверки ingress, cookie, SSE, SEO, .org и identity на staging; запись результатов без подмены локальных проверок production-проверками.

Создание внешних аккаунтов, DNS и деплой не входят в обновление ТЗ и требуют отдельного поручения. Пробелы недоступной истории не заполняются выдуманными цитатами.
