# Авторизация и публичные slug

[Оглавление](README.md) · [ACL](04-roles-and-acl.md) · [Приватность](07-privacy-and-cookies.md)

## Задано

OTP, Google и Facebook как способы входа; публичные slug. Канал OTP, правила объединения аккаунтов и синтаксис slug не определены доступным контекстом.

## Предлагаемая идентификация

Внутренний неизменяемый ID пользователя отделить от email, внешнего provider ID и публичного slug. Хранить связи провайдера по паре provider + provider_subject. Не объединять аккаунты только по совпадению непроверенного email. Привязка нового провайдера требует подтверждённого владения текущим аккаунтом.

OTP: определить email или телефон; задать срок жизни, число попыток, паузу повторной отправки и лимиты по получателю и источнику. Код одноразовый, хранится в защищённом виде, не попадает в журналы. Сообщения об ошибках не должны раскрывать наличие аккаунта.

Социальный вход: сервер проверяет результат входа, ожидаемый получатель и параметры защиты потока. Секреты провайдеров не попадают в браузер. Конкретный OAuth/OIDC-поток проверяется по документации провайдера при реализации.

Предложение для веба: защищённая серверная сессия с HttpOnly-cookie, ограниченным сроком жизни, отзывом и защитой изменяющих запросов. Политика сессий между .org и .com открыта: это разные регистрируемые домены, общая domain-cookie между ними невозможна.

## Предлагаемая политика slug

Slug — читаемый публичный адрес; внутренний ID остаётся ключом связей. Нужны уникальность, нормализация, резерв системных имён и защита от визуально похожих символов. Выбор ASCII или Unicode открыт.

При смене slug сохранять историю и перенаправления для публичных объектов, учитывать повторную выдачу старого имени и приватность. Не раскрывать email или телефон в URL. Slug не заменяет проверку ACL.

Открыто: верификация контакта, удаление последнего способа входа, восстановление, возрастные ограничения, multi-factor authentication, срок резервирования slug и список публичных сущностей.
