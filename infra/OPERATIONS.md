# Эксплуатация

## Первый запуск на сервере
```bash
git clone <repo> /opt/beeloy && cd /opt/beeloy
cp .env.example .env           # заполнить секреты (OTP_HMAC_SECRET и PROXY_SHARED_SECRET — случайные ≥ 32 символов)
bash infra/scripts/update-cf-ips.sh   # CLOUDFLARE_CIDRS для Caddy и правила файрвола; TRUSTED_PROXY_CIDRS=172.30.0.2/32 (адрес Caddy, не Cloudflare)
docker compose --profile prod -f infra/compose/docker-compose.yml up -d
docker compose --profile prod -f infra/compose/docker-compose.yml exec api /api bootstrap-admin --email you@example.com
```
Первый администратор входит обычным кодом на почту, затем выдаёт роли в `/ru/admin/users`.

## Публикация статьи с готовыми переводами (без панели)
1. Для статьи сгенерировать UUID `ID`. Загрузить в S3 (под `S3_PREFIX`):
   - `articles/ID/manifest.json` — формат в `docs/tz/04-backend-features.md §1.1` (**без** статуса публикации);
   - `articles/ID/rev-1/<язык>.json` для каждого готового языка (`"origin": "human"`).
2. Через ≤ 1 минуты Content Sync зарегистрирует статью со статусом `in_review` (`content-sync status`).
3. Модератор открывает `/mod/articles`, просматривает языки, выбирает видимость и нажимает «Publish». **Загрузка в S3 сама ничего не публикует.**

## Машинный перевод (Ollama), вручную
```bash
export OLLAMA_URL=http://gpu-host:11434 OLLAMA_MODEL=<модель> S3_ENDPOINT=… S3_BUCKET=… S3_ACCESS_KEY=… S3_SECRET_KEY=…
translator check
translator article --id <uuid> --locales all          # только недостающие языки; готовые файлы неизменяемы, флага --force нет
translator ui --source contracts/messages/en.json --version 2026-11-04.1 --out ./dist/i18n   # проверить файлы глазами
translator ui --source contracts/messages/en.json --version 2026-11-04.1 --publish           # загрузка в S3, manifest — последним
```
Существующие файлы (человеческие и машинные) утилита никогда не перезаписывает (запись только `PutIfAbsent`), `manifest.json` статьи не меняет и ничего не публикует. Исправление перевода — новая ревизия исходного текста, новые переводы и новое утверждение модератором.
Перед публикацией словарей просмотреть выборку переводов минимум на 3 языках.

## Откат словарей интерфейса
`docker compose exec content-sync /content-sync rollback <версия>` (версии: `content-sync status`).

## Бэкапы (PostgreSQL + S3 одним набором)
Ежедневно в 03:15 UTC контейнер `backup` выполняет `infra/backup/backup.sh`:
1. ставит флаг заморозки записи в Redis (`maintenance`, TTL 1 ч): API отвечает `503` на изменяющие запросы, content-sync пропускает циклы;
2. снимает опись бакета контента, делает `pg_dump`, копирует все объекты (манифесты, все ревизии, релизы словарей), снимает опись второй раз;
3. если описи различаются (кто-то писал в бакет: CLI `translator`, другой сервис) — **снимок не создаётся**, скрипт завершается ошибкой;
4. один снимок `restic` (дамп, объекты, инвентарь sha256, версия схемы, ID набора) в отдельный бакет с отдельными ключами; затем флаг снимается (даже при ошибке).

**Перед ручным бэкапом остановите CLI `translator` и любые операторские записи в S3**: скрипт обнаружит их задним числом, но не может остановить сам. Ключ S3 для бэкапа — только чтение; ключи restic и право удаления бэкапов не должны совпадать с ключами API/content-sync/translator.
Хранение: 7 ежедневных, 4 еженедельных, 6 ежемесячных копий — копия может жить до ~190 дней (указать в политике приватности).

Раз в месяц на машине с docker:
`RESTIC_REPOSITORY=… RESTIC_PASSWORD=… AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… sh infra/backup/restore-test.sh` — проверяет хеши всех объектов, восстанавливает PostgreSQL во временный контейнер, сверяет версию схемы, администратора, соответствие живого индекса файлам, отсутствие неопубликованных ревизий в индексе и отсутствие тел удалённых комментариев. Бэкап считается пригодным только после `restore-test: OK`. Снимок без S3-объектов — FAIL. Цели (проверяемые, не достигнутые): RPO 24 ч, RTO 4 ч.

**Журнал удалений.** При каждом purge аккаунта API пишет в отдельный бакет (`JOURNAL_S3_*`) зашифрованный AES-256-GCM объект `deletion-journal/<user_id>.enc` (только UUID и время; ключ `DELETION_JOURNAL_KEY`, копию хранить вне сервера). После восстановления PostgreSQL из копии, **до открытия трафика**, выполнить `api replay-deletions` с теми же `JOURNAL_S3_*` и ключом: удаления, сделанные после даты копии, применяются повторно (повтор безопасен). Объекты журнала не удалять, пока существует самая старая резервная копия БД. Потеря ключа делает журнал нечитаемым. Если purge последнего администратора заблокирован, команда остановится с ошибкой — решить вручную. Redis не восстанавливается: после аварии очистить его, клиенты пересинхронизируются из PostgreSQL.

## Миграции
Только обратно совместимые. Порядок релиза: `migrate` → новая версия `api`/`content-sync`. Откат приложения — выкатить предыдущий образ; `migrate down` в проде — только вручную по решению человека.

## Диагностика
- `docker compose logs -f api` (JSON, поле `request_id` связывает запрос с ответом `X-Request-Id`).
- `docker compose exec api /api outbox status` — очередь событий.
- Метрики: порт `:9090` внутри сети (`/metrics`), наружу не публикуются.
